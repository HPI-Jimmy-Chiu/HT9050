## A1. web API 的檔案路徑 —— **必須寫真實檔案**（使用者 20260917 早上裁決）

回答的是 `NIGHT_REPORT.md` §0.5 那一題：
web API 讀寫要解析到**真實檔**，還是 `--dry` 造出來的 scratch 副本。

**裁決：真實檔。** 採用 web 同事的做法（他的 review A1/R1），
放棄我們 20260914 那層 `--production-recipe` opt-in。

### 為什麼這是對的

同事量到的缺陷是真的，而且是最糟的一種：

> 在交付包 launcher 的預設 `--dry --allow-cmd` 下，瀏覽器對 `Gerneral.ini` 欄位
> （HW.HandlerSys，214 個）的每一次存檔都寫進 scratch 副本、ack 回 `ok/changed=1`、
> 重讀「看起來正常」—— **然後在伺服器停掉時消失**；
> 而同一頁的 `teach.ini` 欄位卻寫進真實檔案。

**同一個頁面兩種行為，而且「成功」是假的。** 那比「都寫真檔」或「都不寫」都糟。

---

## ⚠⚠ 這條裁決改變了 `--dry` 的意義，這件事要講清楚

**在這之前**：`--dry` 是「不會碰到真實機台檔案」的保險。
**在這之後**：`--dry` 只保護**啟動時的設定載入器**（它仍然會把配方資料夾整份
複製到 `%TEMP%\wb_serve_recipe\` 再重導 `DataPath`）。
**它不再保護 web API 的讀寫。**

⇒ 從此之後，**擋在瀏覽器與真實機台檔案之間的，只剩 `--allow-system-write` 這一道**
（預設關閉）。

實測現況（20260917）：**全樹沒有任何地方傳 `--allow-system-write`** ——
F5 的參數是 `["--dry", "--allow-cmd", "--production-recipe"]`
（`.vscode/launch.json:187`）。所以今天寫入閘實際上是關著的。

> ⚠ **要讓瀏覽器的存檔真的寫進機台，還需要一個另外的決定**（見 §A1.3）。
> 這條裁決只決定了「寫到哪裡」，沒有決定「要不要開始寫」。

## A1.1 `--production-recipe` 怎麼處理

它原本的意思是「讓 API 用真實配方（opt-in）」。裁決之後那變成**預設**，旗標就沒有意義了。

**不能直接刪**，實測有兩個消費者：

```
.vscode/launch.json:187              "args": ["--dry", "--allow-cmd", "--production-recipe"]
tools/webprobe/f5_contract_probe.cjs:28   assert.deepEqual(recipe.args, [...])
```

刪掉會同時弄壞 F5 啟動與那支契約探針。

⇒ **做法**：保留旗標、接受它、但**明白地印一行說它已經是預設**，
不要讓它靜靜地變成 no-op。F5 與探針都照樣通過，而讀主控台的人會知道。

## A1.2 那兩條 `return 2` 安全拒絕**保留，而且改成無條件**

```
no active recipe; refusing to serve
W906_INIDATA_ROOT is redirected; refusing to serve
```

原本它們掛在 `--production-recipe` 底下。裁決之後真實路徑是預設，
**這兩個檢查因此更重要不是更不重要**：

* 沒有作用中配方 → 真實路徑是一段垃圾字串，服務它沒有意義
* `W906_INIDATA_ROOT` 被重導 → 整棵樹在測試圍堵下，「真實」的語意是模糊的

⇒ 兩條都**從旗標底下解開，改成一律生效**。
收尾斷言 `git grep -c "refusing to serve" -- tools/wb_serve.cpp` 仍然必須是 **2**。

## A1.3 ⬜ 這條裁決**沒有**回答的一題

**要不要把 `--allow-system-write` 加進 F5 的參數，讓瀏覽器的存檔真的寫進機台？**

* **不加**（現況）：程式碼在、通路通、但每次存檔都會被閘擋下並回一個明確的錯誤
  （`{"ok":false,"error":"system writes need --allow-system-write"}`）。可以驗前端、
  驗 ack、驗 preview，就是不會真的寫。
* **加**：瀏覽器按存檔會**真的改寫機台的 `Gerneral.ini` / `teach.ini` /
  兩個 csv / `config.ini`**。

這是機台安全決定，**等使用者明確說**。在那之前 WEB-W2b 只落地程式碼，不動 F5 參數。

### B5 判定（20260917 實測，逐條）

原文在 `docs/BU_C_CAMPAIGN_PLAN.md:140-170`。三條**都不動程式碼**，理由各不相同。

#### (1) `MyLaneIo.cpp:261/:326/:389` 的 guard 用未驗證參數索引 → **忠於 golden，不改**

`bIdleNeedCheckSafeDoor[4][64][32][8]`（`cmydef.h:5570`）被
`csystem.cpp:23404`／`:23411` 用呼叫端的 `Ring/IP/Port/Bit` 直接索引，
而 `MyLaneIo.cpp:267` 的 `if(Ring<=0 && IP<=0 && Port<=0 && Bit<=0) return;`
和 `:270` 的 `CheckPortRangeErr` 都在**那之後**。

**這是 golden 的形狀**：`csystem.cpp:23395` 的本體標著 `//Steven 20230703`，
而 `MyLaneIo.cpp:259-260` 的註解明引 BCB6 原註
（「IdleCheckSafeDoorByCylinder is Handler state-machine logic; be careful when modifying!」）。
⇒ 加邊界檢查是**偏離 golden**，依裁準不做。

量到的三件緩和事實（不是藉口，是範圍）：
1. `csystem.cpp:23397` 第一行就是 `if(SystemStart || InitialOK==false) return false;`
   —— 只有在**已初始化且尚未 SystemStart** 的視窗才會讀到那個陣列。
2. 那是**讀**不是寫，越界的後果是讀到相鄰記憶體、可能多跳一次安全門檢查，
   不是記憶體毀損。
3. 要讓 `Ring/IP/Port` 越界，來源是 `IO_Table.csv` 的壞列 —— 那是 🟡 檔，我們不動。

⚠ **但它確實比改動前危險**：改動前 stub 忽略所有參數，這個讀取**根本不存在**。
這一句要留在紀錄裡，因為它是 D-7 唯一「可能出錯」而非「只是抑制動作」的部分。

#### (2) `myswitch.cpp:74` 的 `OutValue` 是命令值 → **忠於 golden，不改 C++**

`TMySwitch::On()` 第一件事就是 `OutValue = true;`，然後才走到 `MyLaneIO.IOBitOn`。
**那是 golden 的順序**，不是我們翻壞的。`WebBridgeTags.cpp:811-824` 自己也已經寫明
「OutValue therefore records what software last COMMANDED」。

⇒ C++ 不動。**但後果是真的**：guard 真的擋下寫入時，網頁仍顯示「已開」，操作員零回饋。
那個修正屬於**網頁層**（把那一欄標成「命令值」或另發一個實際值 tag），
而網頁那一頁是同事的，改它是對外變更 ⇒ **列為待討論，不在這一輪動。**

#### (3) `CheckSafeDoorIsClosed` 的重入 → ⚠ **這條不適用「忠於 golden」的預設值**

它**不是** golden 的形狀差異，是**我們的**：golden 在這條路上的兩個緩衝
（`G-PLC-B` `csystem.cpp:23089`、`G22` 的 0.5 秒 `DoorDelay` 寬限 `:23117`）
在移植樹**都是 `#if 0`**。所以照裁準應該「修（那是回歸）」。

**但「忠於 golden」在這裡會匯入一個已知缺陷。**
那個 0.5 秒 `DoorDelay` 旁路本身就是 HT9045 的已知安全門缺陷
（開機第一次必盲放、之後嚴格交替）。解開它＝把缺陷一起搬進來。

⇒ 兩個選項都不是「忠於 golden」：
| 選項 | 後果 |
|---|---|
| 解開那兩個 `#if 0` | 回到 golden，**同時匯入 0.5 秒盲放缺陷** |
| 加重入保護 | 擋住重入，但**偏離 golden**（golden 沒有這個保護）|

**所以這一條要你選，不是我用預設值帶過。**

⚠ **今天它碰不到**：`MyLaneIo.cpp:139` 寫死 `pIO = new TSimIOBackend()`，
`SetBackend()` 生產端零呼叫點（只有 `tests/` 在用）。
⇒ **IO 還沒武裝，這條重入路徑今天走不到。** 它是「武裝之前必須處理」，不是「現在壞著」。

## B12 S3 缺口 6 的答案：`wb_serve` **物理上指揮不了馬達**（20260917 實測）

§B11 把甲案的難點定在缺口 6：`fAllMotorHome` 初值 false ⇒ `StartFromWeb()`
走 `Home("Home by Start")` 直接 `return false`，而唯一把它寫成 true 的是
`csystem.cpp:9724`（在 `DoHomeProcess()` 裡）。當時我說「要嘛先量馬達層是不是純 Sim，
要嘛加一個 harness 旗標頂著」。

**量完了，答案是可以走誠實那條路。**

### 三個獨立證據

| # | 量法 | 結果 |
|---|---|---|
| 1 | `objdump -p build/wb_serve.exe \| grep "DLL Name"` | **只有 KERNEL32 / PSAPI / USER32 / VERSION / WS2_32 / msvcrt** —— 零個廠商運動 SDK |
| 2 | `grep -E "^\s*(option\|set)\s*\(\s*HAVE_" CMakeLists.txt` | **零筆**。CMake 從未定義任何 `HAVE_*` |
| 3 | `grep -n target_compile_definitions CMakeLists.txt` | 只有 `ht9045_pci1203_probe`（`:2905`）與 `pci1203_linkprobe`（`:2932`）帶 `HAVE_PCI1203=1`，**兩個都是獨立探針 target，不是 `wb_serve` 的相依** |

⇒ `TMySMCMotor` / `TMyMN200Motor` / `TMyEtherCatMotor` 的**類別**有 link 進去
（`nm` 看得到建構子與 vtable），但**每一個廠商呼叫都在 `#if HAVE_xxx` 裡被編掉了**。
`CMakeLists.txt:1245-1247` 自己寫著這個姿態：「the real vendor calls stay behind the
tree's existing `#if HAVE_xxx` posture so the Sim path still links with no SDK present」。

⚠ `TMySimMotor` **也沒有**被 link 進 `wb_serve`（`nm` 命中 0）。所以不是「跑模擬馬達」，
是「馬達物件存在但它的手被切掉了」。

### 這對 S3 的意思

**可以直接補 `DoHomeProcess()` 的呼叫點，走 golden 的真路徑**，不需要造一個
`machine.simHomed` 之類的假旗標。理由：那條路走到底會呼叫馬達的 move 函式，
而那些函式的本體是空的 —— 軸不可能動。

⇒ 使用者選的「甲」（馬達不能動）與「補完整條 HOME 路徑」在這棵樹上**不衝突**。

### ⚠ 這個結論的有效期

它**只對現在這個建置組態成立**。任何一件事發生就作廢：
* 有人給 `wb_serve` 或它的相依加上 `HAVE_SMC` / `HAVE_CMNET` / `HAVE_PCI1203` 等定義
* 有人把 vendor DLL 放進 `EXE/` 並改成動態載入（`LoadLibrary`）
* 換成 MSVC build 且該 build 的旗標不同

**重跑證據 1 和 2 只要三秒。做 S3 的那一天請當場再量一次，不要引用這一節的結論。**
（這棵樹的 memory 有一條就是講「absence claim 會過期」。）

## B13a ⚠ 更正 B13：golden 的 spine 週期量到了，是 **~1 毫秒**

### 真正的驅動者：`uruncontrol.cpp` 的 `TRunControl : TThread`

```cpp
void __fastcall TRunControl::Execute() {
    timeBeginPeriod(1);                      // :45  把系統計時器解析度調到 1 ms
    int ct = 0;
    do {
        Synchronize(ThreadProcess);          // :49  -> MainProc()（:38，InitialOK 才進）
        if (SystemStart == false || iHome == 1 || fContact->fShow == true)
            MySleepEx(1, true);              // :54  閒置／回原點／Contact 開著

            else MySleepEx(1, true);         // :65
        }
    } while (!bEnd);                         // :68
}
```

| 機台狀態 | `MainProc()` 週期 |
|---|---|
| 閒置 / `iHome==1` / Contact 畫面開著 | **~1 ms** |
| 運轉中 | 3 個 tick 約 2 ms（每第 3 個不睡） |

⚠ **`Synchronize()` 代表 `MainProc()` 實際跑在 VCL 主執行緒上**，不是那個 worker
執行緒。worker 只負責節拍。這一點對移植很重要 —— spine 與 UI 共用同一條執行緒，

## C2 ⚠ 啟動時印的那句 WARNING **是錯的**，而真正的危害更大

原文（`wb_serve.cpp`）：
> the loader flushes its own copy **at exit**, which can undo browser edits …
> Prefer `--dry` …

**兩半都不成立**，而且它推薦一個已經退役的旗標：

1. `CloseGeneralIniFile()` 只寫在 `if (dry)` 裡面（退出路徑）。零參數 = `dry=false`
   ⇒ **退出時根本不會呼叫它**。
2. 就算呼叫了也是 no-op：vclcompat 的 `TIniFile` 是 write-through
   （`IniFiles.cpp:281` 的 `UpdateFile()` 是 `if (!writeThrough_)`），沒有東西待 flush。

**實測**：server 起跑 8 秒後在磁碟上插入一個沒有任何程式讀的鍵，
它**逐位元組活過了退出**（MD5 全程不變）。

### 真正的危害：兩個互不知情的 writer，其中一個是整檔覆蓋型

`TIniFile::WriteString` → `store_.WriteRaw` + `flush()`，而 `flush()` 是
`store_.SaveToFile(FileName)`（`IniFiles.cpp:277-279`）——
**用 `OpenGeneralIniFile()` 當下的記憶體映像，把整個檔重寫一遍**。

Win32 的 `WritePrivateProfileString`（這個類別在模擬它）是就地編輯、
會吃到磁碟當下的內容；我們的可攜 store 不會。所以：

> **寫一個鍵 = 無聲地把 server 啟動以來磁碟上的所有變動回捲。**

而瀏覽器是第二個 writer：`system.file.put` 走 `ApplyIniGuarded(path,…)`，
外科式編輯、自己留備份、**完全不碰 `INIFileGeneral`**。沒有任何東西調解這兩者。

### 誰會觸發它 —— 28 個呼叫點，其中一個正是 START

`WriteIniDataGeneral` 全樹 28 處（排除 `common.cpp` 與 `tests/`）：

`WebStart.cpp:1806` 是 `StartFromWeb()` 裡的
`WriteIniDataGeneral("System", "bInitialCleanCount", 0)`（golden :5323）。

## C7 Release 側延後，以及 `WB_*` 那三支測試在負載下會假紅

### C7.1 使用者裁決：先穩定 Debug，Release 之後補

|---|---|---|
| `build/` | **空字串**（無最佳化） | **F5 跑的、機台上測的那顆** |

| `build_<tag>r` | `Release`（`-O3 -DNDEBUG`） | **目前沒有人在跑** |

`build_bu4br/` 15,739,172 B（小一截 = 有最佳化）。

⇒ 延後 Release 不是「放棄一半驗證」，是**把驗證對齊到實際在跑的組態**。

### C7.2 延後的代價，三條，第一條是結構性的

1. ⚠ **`-O3` 會改變 x87 的中間精度。** `-O0` 時中間值落回記憶體（截成 double），
   `-O3` 時留在 80-bit 暫存器。而 `CLAUDE.md` 對主 oracle 的定義是
   「**唯一重現 BCB6 x87 算術，不可替換**」，`CMakeLists.txt` 裡**沒有**
   `-ffloat-store` / `-mfpmath` / `-fexcess-precision` 任何保護（grep 0 命中），
   樹裡有 **8 支測試**在用 epsilon 比對浮點。
   ⇒ 延後之後，「數值忠實度」只會在 `-O0` 上被量到。
2. `-DNDEBUG` 關掉所有 `assert()`。
3. `-O0` 下良性的 UB 在 `-O3` 下會變成真的 bug。

### C7.3 兩個接受的條件（已落實其一）

* **條件一：「Release 未跑」必須大聲，不可靜默省略。** ✅ 已實作 ——

  補驗條件＋那 8 支測試的清單，且最終判定字串變成

  ⚠ 這條的理由跟這支工具當初存在的理由是同一個：w34 在紅燈上 commit 而
  記成綠燈，機制是「**證據的缺席長得跟證據一樣**」。少跑一側也是同一個形狀。
* 條件二：這棵樹出任何東西之前必須補驗 Release，**第一個看那 8 支浮點測試**。

## C9 `W906_Trace` G6 偶發失敗 —— 測試的觀測點不健全，不是產品缺陷

### C9.1 觀察到的事實

出貨組態 Debug gate 第一輪（20260918 20:00）冒出一支**不在常駐五項裡**的失敗：

| 次數 | 條件 | G6 失敗 |
|---|---|---|
| 1 | 完整 gate 第一輪（~230 支連跑） | **1** |
| 8 | 單獨重跑，機器空閒 | 0 |
| 40 | 單獨重跑，10 個 cc1plus 壓著 | 0 |
| 1 | 完整 gate 第二輪（同一顆 binary） | 0 |
| | **合計 50 次執行，1 次失敗** | |

### C9.2 機制：事後無法觀測的相等性

`PART G` 有五個 `iTimeFormat` 案例，**只有 case 0（`iTimeFormat==1`，16 byte）失敗**。
那是五個裡唯一帶 `SystemMSec/10`（百分之一秒）的格式；其餘四個是「秒」解析度。

生產碼這一側**沒有競態**（`SECSGEM/uHGemEquipment.cpp`）：

* `GetTimeInfo()`（`:3532`）只取樣 `Now()` **一次**，同時填 `GemClock`
  與 `SystemYear..SystemMSec`
* `DoTraceDataResponse`（`:4651`）呼叫它一次，之後的 ladder 直接用那批成員欄位
  重排，**不重新取樣**

⇒ 發出當下 `onWire == GemClock` 是決定性成立的。

**問題在測試的觀測點**：G6 讀 `g.GemClock` 是在 `DoTraceDataResponse` 回來**之後**，
中間隔了 `SendLocalData()`。而 `GetTimeInfo()` 在這個檔裡有 **13 個呼叫點**，
其中包含 socket 事件處理器（例：`clientGemDisconnect` `:3637`）。
任何一次後續呼叫都會**同時覆寫** `GemClock` 與 `System*` 欄位。

⇒ **事後沒有任何穩定的觀測點可以證明「發出當下相等」。**
`GemClock` 和 `System*` 都會被覆寫，所以也不能改成比對成員欄位——那一樣會被蓋掉。
單次失敗率若約 0.5%（＝兩次取樣間隔 / 10 ms），50 次只中 1 次完全相容。

### C9.3 裁決：不在 T1 修，記為 T7 債務

* **不是回歸**：與 `SOFT_SIMULTE` 組態無關（它是 SECS/GEM 時戳格式化），
  而且在**同一顆出貨組態 binary** 上 49/50 通過
* **不加進常駐失敗清單**：那等於授權自己未來忽略它的真失敗
  （`a-gate-that-cannot-fail`）
* **要修的是測試，不是產品**。可能的方向（未驗證，留給 T7）：
  1. 讓 fixture 保證發出後不會再有 `GetTimeInfo()`（要先查清楚那一次是誰叫的）
  2. 在 `DataItemOut(HType.ASCII_TYPE, str)` 當下就攔截比對，而不是事後
  3. 若前兩者都做不到，就照 X3 的精神**誠實降級**：明講 G6 只能 pin 到「秒」，
     並為百分之一秒那一位另外寫一條有界差異的斷言

⚠ **不要**用「重跑就過了」當結論。那句話對真回歸也永遠成立
（`always-true-excuse-is-the-thing-to-measure`）。這裡能下結論是因為量到了
**機制**（唯一失敗的是唯一帶次秒解析度的格式）與**分母**（50 次），不是因為它重跑會過。

### C9.4 同類清單

`W906_Trace` 是第四支，但**成因不同**：C7.4 那三支是逾時，這一支是觀測點競態。

### C13.2 `IniFiles` 常駐失敗的根因，與它對 §C2 修法的影響

`IniFiles` 在常駐五項裡。實測它失敗的是哪三條（`tests/test_IniFiles.cpp:244-247`）：

| 斷言 | 這台機器實際值 |
|---|---|
| `[System] IO_CARD_TYPE == 2` | **1** |
| `[System] TTL_CARD_TYPE == 2` | **0** |
| `[TempCtrl] HEATER_CTRL_TYPE == 4` | **2** |

（同一段的 `MOTION_CARD_TYPE == 1` 與 `INDEX_MOTION_CARD == 0` 通過，所以不是整段失效。）

那段測試對 `D:\HT9045\system\Gerneral.ini` 硬編碼了**某一台機器的組態值**。

⇒ **`IniFiles` 的常駐失敗是「測試把一台機器的組態當成普世真理」，
不是 `TIniFile` 實作的缺陷。**

**這推翻 §C2 結尾的顧慮**：那裡寫著
「⚠ (a) 動到 `vclcompat`，而 `IniFiles` 正在常駐失敗清單上」，
語氣上把兩件事綁在一起。它們沒有牽連 —— 常駐失敗是組態值比對，
與 `flush()` 的語意無關。⇒ **修法 (a)（`flush()` 改成寫入前重讀再套用單一異動）
不會被那支測試擋住。**

⚠ 順帶一個更該注意的推論：**這支測試在任何組態不同的機器上都會紅**，
包含同事的機台。一個「換台機器就紅」的常駐失敗，等於訓練所有人忽略它 ——
而它同時還守著 `TIniFile` 其餘幾十條真正的行為斷言。
⇒ 建議（未做，等使用者裁決）：把那五條組態值斷言改成
「印出來 + 斷言型別/存在性」，把「值等於多少」留給一支機台專屬的驗收腳本。

### C14.2 ⚠⚠ 掛鐘全域從來沒有被更新過 —— 這個行程印出的每一個時間戳都是 9999

第一次跑完 `tools/realfile_guard.py check` 抓到：

```
--- D:\HT9045\config\config.ini
< Lot ID=1
< LotStartTime=2026-09-11 10:38:52
---
> Lot ID=W906TESTLOT
> LotStartTime=9999-9999-00 9999:9999:9999
```

`Lot ID` 變了是預期的（那就是 `lot.start` 的事，已還原）。
**`LotStartTime` 不是。**

根因：`cmydef.cpp:292`

```cpp
Word SystemYear=9999, SystemMonth=9999, SystemDate;
```

**初值就是哨兵 9999**，而更新它們的 `GetTimeInfo()`（`cpublic.cpp:450`，
golden `cpublic.cpp:296`）在 `wb_serve` 這個行程裡**從來沒有被呼叫過**。
golden 在兩個地方呼叫它：`TfMain` ctor（`main.cpp:1683`，開機一次）與
`TfMain::ProcessTimeUpdate()`（`main.cpp:7812`，週期性）—— 這個行程兩個都沒有。

⚠ **影響範圍遠大於 lot.start。** 全樹有 100+ 處用這六個全域組時間字串或路徑：
BarCode 的日期資料夾（`BarCode.cpp:6745` 的 `%04d_%02d_%02d`）、
Jam 報表的年份目錄（`cprod.cpp:1070`）、OEE 的起訖時間（`cprod.cpp:941`）、
ATC 的 `@HANDLER_TEST_START`（`ATCInterface.cpp:2154`）…
**只要 wb_serve 走到其中任何一處，寫出去的就是 9999。**

⇒ 修法是整合接縫，不是翻譯偏離：把 `GetTimeInfo()` 接進 `PumpTick()`
（`WebBridgeTags.cpp`，這個行程唯一的週期性入口），對應 golden 的
`ProcessTimeUpdate`。`GetTimeInfo()` 本身是逐字翻譯的，一個字沒動。

### C14.3 這兩件事情的共同形狀，值得記

兩個都是**建置綠、跑起來錯**，而且兩個都**不是翻譯錯**：

| | 缺什麼 | 為什麼建置看不出來 |
|---|---|---|
| C14.1 | 全域指標**從未建構** | 型別齊全，deref 是合法 C++ |
| C14.2 | 全域**從未被更新** | 有定義、有初值，只是初值是哨兵 |

⇒ **移植樹的「這個符號存在」有三種強度**，翻譯前要分清楚：
1. 型別存在（能編）
2. 實例存在（不會 NULL deref）
3. **有人在維護它的值**（讀到的不是初值）

`nm --undefined-only` 只看得到第 1 級。第 2、3 級要跑起來才知道，
而 §0.6 的備份紀律是目前唯一會抓到第 3 級的機制 ——
這一次它抓到的是寫進真實檔的 `9999-9999-00 9999:9999:9999`。
