### B. 跟 tick（NIGHT_REPORT §0 #127）有關的——**這一段 main 也一樣**

- **每一拍都重建網頁快取（約 148 KB 的 io-runtime＋65 KB 的 motor-runtime JSON）並發布 1,808 個 tag**（`wb_serve.cpp` 的 `if (pumpBeat) … g_apiCacheDirty = true`、`publishNow = pumpBeat || …`；**main `445275d1` 的 :4622／:5963 也是這樣**）。`AI(W906-TICK-100)` 註解寫的「apiCache／publish 不隨節拍增加」跟程式不符：tick 越快，這部分就越重（實測 100 ms＋IO 執行緒是每秒 16.6 次重建，500 ms 是 6.4 次）。

## Part 2 -- the four reviews (English, as returned; all line numbers at machine tree `98c94aad` unless stated)

### Q1 -- verdict: RISK

> Q1: After IOTHREAD (6f25a2d4f, machine tree 98c94aad), are ALL Advantech PCIE-1203 SDK calls (Acm_* and the port wrappers that reach them) made only on the IO thread that owns the card? List every SDK call site reachable at runtime, the thread each runs on, and flag any call that can still run off the IO thread.

Short answer: yes while the IO thread is running. Every Acm_* call built into wb_serve then runs on the IO thread. A few calls run off it by design, at boot, at shutdown, and in sessions where the thread never started. The real risk is a failure path: if Pci1203IoThreadStop(5000) times out, nothing later checks for that, and the close sequence can recurse without limit through the proxy or close/delete the monitor while the IO thread is still alive.

OFF THE IO THREAD BY DESIGN
- Boot: Open runs on the main thread before the IO thread exists (wb_serve:4460, then mon:3113).
- Shutdown: after the IO thread is joined (wb_serve:5982), ShutdownSequence calls Execute directly on the main thread (MainClose:998/693), and Pci1203MonitorDisable runs Close on the main thread (Acm_AxClose/Acm_DevClose).
- Whole session on the main thread: if the monitor is not open at boot, the IO thread never starts (mon:4551; the only start call is wb_serve:4496).

FLAGGED
- Stop timeout: Stop's timeout branch (mon:4591-4592) returns without clearing `running` or the thread handle, and nothing downstream checks it.
  - RunSync's "thread ended, run it here" fallback (mon:4518) calls a lambda that calls the proxied method again, so Execute, Vc8SdoReadI16 and SetTorqueFocusAxis recurse without limit.
  - Pci1203MonitorDisable then runs Close/delete with the IO thread possibly still alive.
  - The same state can arise from the boot path (mon:4575), which still logs "the IO stays on the main thread".
- A race in RunSync when CreateEventA fails (mon:4510 vs :4479/:4481).

### Q2 -- verdict: BUG

> Q2: Where the main (tick) thread, or the web thread, now asks the PCI-1203 IO thread to do something and waits (the proxy waits added by IOTHREAD 6f25a2d4f, tree 98c94aad), can that wait hang or deadlock? Covers waits without a timeout, waits while holding a lock the IO thread needs, lock order, an IO thread that is stopped, not started or crashed, the exit and shutdown order (MainClose.cpp, tools/wb_serve.cpp), and SOFT_SIMULTE / no-card builds.

There is no deadlock cycle. The IO thread never waits on the tick thread. Its two critical sections (queue and snapshot) are never nested and never held across a wait or a request. The only lock the tick thread holds across a proxy wait is the Index-Z GaliRoute lock (s_cs), and the IO thread never takes it. All 14 non-test call sites of the 3 proxied functions are reached from tick-thread code. The web socket thread only enqueues and never makes a proxy wait.

Builds where the IO thread does not start fall straight through to the old path: not started, no SDK, and ctest. W906_PCI1203_IO_THREAD does not depend on SOFT_SIMULTE, so a SIM build that opens a real card starts the IO thread just like the ship build.

On the machine, the one 6-minute session with the IO thread (21:01:40–21:07:40) showed no hang:
- 26 DO clicks were acked in 31–172 ms.
- The Q44 stop was confirmed in 44 ms.
- Shutdown took 3.7 s.

The waits are still not safe in the failure paths:
1. **The proxy wait is INFINITE with no liveness check.** The heartbeat function has 0 callers. If the IO thread stalls, the tick loop keeps running on a frozen IO image with no WAR16152, then blocks for good at its next card command. The watchdog blames whatever phase the caller marked last, not the IO thread. The hang is no more likely than before, but it is harder to see.
2. **A timed-out Pci1203IoThreadStop leaves `running` = 1.** Once the IO thread has ended, RunSync's "thread ended, run it here" fallback calls the public, still-proxying function, so it recurses without bound (stack overflow). If the thread never ends, the call waits forever.
   - At exit, a poll longer than 5 s triggers this: the close sequence crashes, or the 15 s exit watchdog kills the process. Pci1203MonitorDisable can also delete the monitor while the IO thread is still polling it.
   - At boot, a first poll longer than 20 s triggers it. The log then says "the IO stays on the main thread", which is false: the main thread never polls the card again, and the first card command crashes or blocks.
3. **A failed Rescan leaves the IO thread alive but no longer publishing.** Poll returns before the guard that publishes a copy. The main thread's view stays "card open, stations in OP", so the WAR16152 that LinkWatch was written to raise for exactly this case cannot fire, and "newer sample" waits never finish.
4. **Rare race if CreateEvent fails.** The fallback can return before the request runs, and the request then runs on a dead stack frame.

### Q3 -- verdict: BUG

> Q3 -- With W906-IOTHREAD (6f25a2d4f; tree 98c94aad) the main thread reads PCI-1203 IO/axis state from a COPY the IO thread publishes after every poll (~10 ms gap). Are the semantics right? Torn/non-atomic reads, staleness bounds, write-then-read before the next poll, input edges shorter than one poll (lost pulses), ordering between motion-done flags and IO, and golden logic that assumed a fresh hardware read right after a write.

All line numbers are at commit 98c94aad unless stated otherwise. The core published-copy mechanism works. Only the tick (main) thread reads the copy (W906IoView_). The copy changes in only two ways: the main thread's own Adopt (under g_w906IoScs), and W906IoPatchDo_ on the IO thread while the main thread is blocked in RunSync. So in steady state there are no torn reads. Reading back a DO byte right after writing it is consistent, because ForceDoReread updates the published and staged copies before Execute returns. Motion-done is protected wherever a Pci1203IoFreshMark mark is compared with `<=` (engine MotionDone never trusts a pending sample).

The semantics are still wrong in several places:
(1) If a card rescan fails, the IO thread's Poll() returns before IoPass_ is built, so it never publishes again. The main thread then keeps reading the pre-rescan copy as "open, valid": inputs are frozen and the WAR16152 link-lost watch cannot fire. This breaks the tree's own "no frozen inputs" / "a failed rescan leaves the monitor CLOSED" contract.
(2) One "value must come from a later poll" site was not converted: the IndexZTorqueCore arm (E-038, which its own source labels SAFETY). It can accept a torque sample from a poll that started, or had even finished without being adopted, before the arm.
(3) FreshMark broke three sites that use the mark in a subtraction or as a lower bound: the Q44 shutdown read-back wraps around and counts as "fresh" at once; the GaliRouteCore window after a stop from another caller is inactive until the main thread catches up; RouteSiblingHoming wraps (no live caller today).
(4) After a successful rescan, and until the next adopt, the DO slot is picked from the old published map but executed against the IO thread's new map.
(5) Nothing bounds or detects staleness. The snapshot has no timestamp. The heartbeat has no consumer. Each adopt pushes nextIo another 200 ms ahead, so the timer fallback of the IO branch effectively never fires. The link and module watches only run on a new publish, and they evaluate the copy itself.

Lost pulses and the DI-before-axes order inside a poll are the same as before. There is still no edge latch, and MainProc only sees the snapshot current at its 100 ms beat. The difference now is that any command can run at a yield point in the middle of a poll. For golden write-then-read: output status is a pure OutPortData cache read, exactly as in golden, so it is unaffected. A DI read after a write never saw post-write state within one engine pass in the port (it goes through the route snapshot, while golden calls Acm_DaqDiGetBitEx; MySleep is a plain ::Sleep). IOTHREAD does not change that.

On-machine coverage: the 21:01:40-21:07:36 IOTHREAD session only ran 26 io.btnPanelClick commands, with no motion, HOME or START. Its STREAM/FASTCLK numbers cannot be compared with the 17:33 session, because kServeTickMs also changed from 500 to 100 ms in between.

### Q4 -- verdict: RISK

> Q4: With IOTHREAD, can the machine main tick go back from 500 ms to 100 ms? (a) What does the main tick still do each cycle that is expensive now that the IO scan runs on its own thread? (b) What do the 10-05 oplog FASTCLK/STREAM lines show before 21:01:40 (no IO thread) versus 21:01:40–21:07:40 (IO thread on)? What can that 6-minute window prove and not prove, and what should EastSun measure?

Short answer: the machine is already on a 100 ms tick. In the one 6-minute idle run, IOTHREAD made 100 ms workable, but it did not lighten the main thread, and nothing yet shows 100 ms is safe under load.

Premise correction: kServeTickMs is 100 at 98c94aad, at 6f25a2d4f and at its parent (tools/wb_serve.cpp:2944, one unconditional constant). The machine went from 500 to 100 with PKG-147/148 (76a370f5e, 18:29; Jerry: the machine applied package 148 at 18:28). So every 10-05 session before 21:01:40 ran at 500 ms with the 1203 Poll on the main thread. The only IOTHREAD session (21:01:31–21:07:40, Debug x86 exe built 21:01:11) ran at 100 ms. Jerry recommended 'machine 500 / SIM 100', but no code implements it.

(a) Code. With Poll off the main thread, the expensive per-cycle work left on it is the web feed:
- Every 100 ms pump beat runs PumpTick/MainProc.
- The same beat marks the HTTP cache dirty (:4623). W906_ApiCacheRefresh then rebuilds IoRuntimeJson (~148 KB) and MotorRuntimeJson (~65 KB), and the op-log motor diff runs inside the same timed section (:6450).
- The beat also forces a 1,808-tag PublishHandlerTags (:5964).
- IOTHREAD adds a second trigger. The IO thread polls back to back with a 10 ms gap. Each newly published poll wakes the IO branch (:4672), which marks the cache dirty again (:4683).
- The written rationale for 100 ms (:2938-2940: 'apiCache/publish do not grow with the tick') is contradicted by :4623 and :5964.

(b) Log. The first window of each session is excluded. Baseline = sessions 1–12 (same build_integ_dbg_x86 dir): 3,635 ten-second windows / 843,570 passes. IOTHREAD = 34 windows / 9,089 passes. Before → after:
- Passes ≥100 ms: 18.90% → 0.31%. Per 10 s: median 50 (exactly the 200 ms Poll clock) → 0.
- Worst pass per 10 s: median 126.6 → 93.8 ms, p95 1,024 → 902 ms, max 85,247 → 1,489 ms.
- Per-window mean pass: median 28.99 → 27.77 ms, p95 46.6 → 39.9 ms. Pass-weighted mean: 25.9 → 25.2 ms.
- Per-pass median: from under 20 ms to about 30 ms (the log only gives 20/30/100 ms buckets).
- Main-thread busy share: 59.4% → 67.4%.
- apiCache: 6.4/s × 19.4 ms = 126 ms/s → 16.6/s × 29.6 ms = 475 ms/s. Publish: 25 → 99 ms/s.
- 20 ms heater beats achieved: 41.8% → 49.8%.

Like-for-like (idle, one web client; last 500 ms session, 193 windows, vs 12 IOTHREAD windows): busy 62.9% → 59.5%, worst-pass median 128 → 80 ms, passes ≥100 ms 24% → 0.16%. Taking Poll off the thread freed about 380 ms/s, and the extra rebuilds and publishes took about 345 ms/s back. The baseline reproduces the machine's own WORKLOG 125 statistics (p50 29 ms, worst-pass p50 127 ms, heater 42%).

What the window proves: IOTHREAD removes the Poll stalls, and a 100 ms loop keeps up while idle.

What it cannot prove:
- Behaviour under load: there was no Servo ON, HOME, run or Motor Test in the window.
- Which change caused what: tick 500→100, timeBeginPeriod(1) and the modal fast clock all arrived with PKG-148, then IOTHREAD came. Web clients also went from 1 to a median of 3.
- Rare tails: 5 of 30 idle windows had a pass ≥200 ms, against 3.1% at baseline. The 1,489 ms pass at 21:03:01 has no logged cause.
- Release-build behaviour (both runs are Debug x86).
- The newest tree: 98c94aad adds a per-pass SrDiag publish that the measured exe did not run.
