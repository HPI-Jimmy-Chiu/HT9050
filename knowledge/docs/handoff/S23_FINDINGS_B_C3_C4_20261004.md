## Rule recommendations (C3 / C4, plus input for C1)
- **C3 cylinder layer** (details below): on HT9050, `Push()` / `Pop()` return true at once when `Enable==false` (they never look at Enable today);
  output-off / sensor-on rows are table errors logged at boot (C5); raw `OnStatus` / `OffStatus` / `GetOutBit` keep their meaning, and the few call
  sites that use them -- or `OnSensor` / `OffSensor` -- as an ERROR test get the golden `Enable &&` guard (item 4 above is one).
- **C4 sensor layer** (details below): a per-sensor HT9050 absent policy -- `neutral` (today) / `reads-on` / `reads-off` / `alias=<input>` /
  `required` -- applied after golden's force-enable passes (doors), op-logged at boot; never one blanket rule. Doors: force only the doors whose row
  is Enable 1. EMG: name the real EMG input or alias SnMotorPower. Several "absent" process sensors have an Enable-1 HT9050 twin to alias.
- **For C1 (NB2-1, motor layer)**: an absent axis must report "lane absent", not "in position" (In Shuttle 2); the Index pair calls need a
  pair -> MTestZ1 rule or a ported `DoTestHead` (Steven's Q94).

### Q1 -- where `Cylinder[].Enable` comes from
`cinitial.cpp` `InitCylinder()` (~:4851-5040), IO_CARD_TYPE = PCI1203_IO (HT9050: IO_CARD_TYPE=4):
- `Cylinder[i].Enable` = the **output row only** -- the IO_Table row whose Alias is exactly the cylinder name (`C_x`):
  `iEnable==1 && OutRingUse!=""` (Port != -1) (~:5018-5021). Missing row -> false (~:4993-4996).
- `OnSenEnable` / `OffSenEnable` come independently from the `C_x_On` / `C_x_Off` rows (~:4912-4980): Enable==1 and a non-zero address.
- So "output row Enable 0, `_On` / `_Off` Enable 1" (C_Shuttle1Floodgate, C_OutShuttle1Floodgate in the live table) gives
  `Enable=false, OnSenEnable=true, OffSenEnable=true`.
- (Loader side, ST01-E2's reference f999c9c9: a row with an empty Port / Bit is forced Enable 0 at load, `database.cpp` ~:1980.)
- **Boot overrides beat the table** (area T, T11): right after the table binding, `InitCylinder` (~:5236-5292) forces cylinders off by machine
  setting -- `AUTO_EMPTY_COLOR==0` (HT9050) -> C_EmptyLoaderZ_Select, C_ColorLoaderZ_Select, C_Empty_Fix, C_Color_Fix, C_Color_Up, C_Color_Middle,
  C_Empty_Up, C_Empty_Middle = false, and `USE_AUTO_RETEST==0` -> C_Auto1-3_Up, C_Auto1-3LoaderZ_Select = false, **even where the live row is
  Enable 1** (C_Empty_Up, C_EmptyLoaderZ_Select, C_Auto1/2/3_Up, C_Auto1/2/3LoaderZ_Select). So "Enable 1 in the table" is not the final answer;
  this also shrinks HOME's reset list (REQUEST s5 lists those cylinders as normal). EastSun: should these golden overrides apply on HT9050?

Consequences on HT9050:
1. **Absent cylinders (no row, or output and sensors all off) "succeed" silently**: Push/Pop true after 0.1 s, OnSensor/OffSensor true. Safe for flows,
   wrong only if the cylinder physically exists (then the table is wrong).
2. **Mismatch (output off, sensor on) never reaches position**: alarm or endless false. Live table: C_Shuttle1Floodgate, C_OutShuttle1Floodgate.
   Their HOME use (step 1) is gated by `SHUTTLE_FLOODGATE==1`; HT9050's Gerneral.ini has `SHUTTLE_FLOODGATE=0`, so not reached there today
   (other sites: see B).
3. **Raw `OnStatus()` / `OffStatus()` / `GetOutBit()` used as an in-position test** read "not there" forever for an absent cylinder -- every such site is a
   hang / wrong-branch candidate (listed in B).

### C3 rule proposal
Precedent: golden HOME's reset rule treats `Enable==false` as "no reset needed" (port `uhome.cpp` SetCylinderResetStateHomeBegin ~:226-234,
"Steven 20240123: 改用enable確認氣缸是否要復歸"), and `OnSensor()` / `OffSensor()` already answer true for a disabled cylinder.
1. **`Push()` / `Pop()`: `Enable==false` -> return true at once** (no output, no sensor wait), HT9050 branch only (`W906_IsHT9050()`); other machines golden.
   This makes Push/Pop agree with OnSensor/OffSensor and removes the mismatch hang in one place.
2. **Mismatch rows are a TABLE error, not a code case**: log them once at boot (op log, no blocking popup -- that is C5's boot check), e.g.
   `C_Shuttle1Floodgate: output Enable 0 but _On/_Off Enable 1`. EastSun decides per row: enable the output (the cylinder exists) or disable the sensors.
3. Keep `On()` / `Off()` no-op and the RAW `OnStatus()` / `OffStatus()` / `GetOutBit()` semantics (the IO page and diagnostics need the true reading);
   instead fix the few call sites that use a raw read as an in-position wait (B list) -- or switch them to `OnSensor()` / `OffSensor()`.
4. Risk: a cylinder that physically exists but whose output row was disabled by mistake now "succeeds" instead of hanging -- the flow moves on without
   it. Same trade-off golden's HOME rule already accepts; the boot log (2) is what catches it.
5. **The layer's "true" is right for WAITS and wrong for ERROR TESTS.** Some call sites read `OnSensor()` / `OffSensor()` as "the cylinder did NOT
   move" (an error). Example (area R, High): `CheckLoaderHasTray` (`ainarm9045.cpp` ~:11912) treats `Cylinder[C_TrayY_Fixer].OffSensor()==true` as
   "fixer failed"; with C_TrayY_Fixer Enable 0 that is always true -> JAM0903 on every loader pick (3 tries). These sites need the golden guard
   `Cylinder[x].Enable && ...` at the call site (or the table fixed if the fixer exists) -- no layer rule can serve both readings.

## C4 -- sensor layer (per sensor, never one blanket rule)

### What the layer does today (`mysensor.cpp`)
A sensor whose IO_Table row is missing or Enable 0 (or has an empty Port / Bit -> forced Enable 0 at load) returns
**`IsOn()` = false AND `IsOff()` = false AND `Status()` = false** (`State=-1`). Exceptions: `SenBit0..19` are always enabled; with
`Enable_PLCSafety_IO` + ePLCbase rows are forced on (not the case on HT9050: SafePlcIO=0).
So the same physical condition reads differently depending on how the call site asks:
- `if (Sen[x].IsOff()) alarm/stop` -> never fires (the check is silently off);
- `if (Sen[x].IsOn()) ...` -> "absent / not pressed";
- `while (!Sen[x].IsOff())` / a state machine waiting for IsOff -> **never ends**;
- `!IsOn()` -> true.
A blanket "missing = on" or "missing = off" would therefore be wrong for half the call sites, and for safety inputs it would either lock the
machine or hide a hazard. Hence a per-sensor rule.

### Proposed mechanism (HT9050 branch; other machines keep golden)
1. **Per-sensor absent policy**, one line per sensor in a machine file (e.g. `machines\HT9050\SensorAbsent.ini`, loaded at boot after IO_Table):
   - `neutral` (default = today: IsOn false, IsOff false),
   - `reads-on` / `reads-off` (the flow sees a fixed value -- only for process sensors the machine does not have),
   - `alias=<other sensor>` (read a different, existing input -- e.g. SnSystemPower -> SnMotorPower),
   - `required` (the machine MUST have it: boot op-log ERROR + START refused with the sensor named).
   Only consulted when the row is missing / Enable 0. Every non-neutral line is written to the op log at boot.
2. **Boot check** (shared with C5): list every sensor the reachable code reads whose row is missing / Enable 0, with its policy. No popup.
3. Call sites that wait on `IsOff()` of an absent sensor get the policy value instead of hanging; error checks read "no error" when the policy says
   `reads-on`/`reads-off` accordingly.
4. **Hook it AFTER golden's force-enable passes.** Golden re-enables some sensors in code after the table binding (`InitialSafeDoor` doors 1/2/3/6-9,
   `InitialHeaterDoor`, `SenBit0..19`); the HT9050 policy must be applied after those, or the doors stay forced on (see the door row).

## Appendix B -- method

- **Code:** GitLab main dfa9a22c (`D:\AI_TempFile\st01-s23\tree`, a detached read-only worktree). The machine runs the SHIP build: `SOFT_SIMULTE` and `DEBUG_HOME` are not defined, and `#if 0` is dead. Line numbers drift against the machine tree 1ca2340, so every finding cites file + function + line.
- **Tables:** the LIVE files from EastSun's dispatch 7 (GitHub HT9050 machine/integ-ioweb 75b31e2, `dispatch/20261003_home_tables`). Machine settings: the 10-03 23:34 snapshot (`machine_params/D_HT9045_system/Gerneral.ini`, `D_HT9045_config/config.ini`).
- **Step 1, mechanical scan** (`b_c3c4/xref.py`): every `Cylinder[]` / `Sen[]` / `SW[]` / `MOT[]` use in the SHIP-visible code, with its enclosing function and method, bound to its live row.
  - IO binds by name: `Cylinder[C_x].CylinderName = "C_x"`, plus the `C_x_On` / `C_x_Off` rows. `Sen` / `SW` bind by `.Name`.
  - Motors bind by the Motorname column (`"M%02d"` of the enum index, `cinitial.cpp` ~:4155-4180).
  - Result: 4,175 IO references (Cylinder 1,346, Sen 1,762, SW 1,067) and 1,954 motor references whose row is missing, Enable 0, or (for motors) not an enabled PCI1203 axis.
- **Step 2, risk classes** (`classify.py`, `classes2.json`):
  - cylinder Push/Pop with output off but sensor on;
  - raw `OnStatus` / `OffStatus` / `GetOutBit` reads;
  - sensor reads;
  - switch actions;
  - motion on SMC / MN200 / missing axes.
  Statements that already ask `.Enable` are counted as guarded.
- **Step 3, semantic review** by area, with reachability decided from HT9050's Gerneral.ini / config.ini and the customer code (957 = CC_PTI).
  - Model 9050GPIB decodes as HT9046_LS, so HT9046_LS flows are the ones reviewed.
  - One row per (function, table name). Severity H = hang / alarm / physical wrong move in a reachable auto-run, HOME-adjacent or safety path; M = operator-visible; L = silent no-op or fragile.
- **Limits:**
  - IO indexed through an array is not in the scan; Appendix A expands the static arrays.
  - Run-time-filled arrays (`SensorIndex[]`, `iC_DoorLock[]` ...) were followed by hand only where a reviewer met them.
  - Recipe values (Auto Clean on/off, NN mode, select arm) are not in the inputs; rows that depend on them are marked conditional.
  - Nothing was edited, built or run. "Fixed?" is "no" throughout.
