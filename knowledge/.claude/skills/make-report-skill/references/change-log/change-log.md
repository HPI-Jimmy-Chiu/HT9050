# Change Log（當日變更紀錄）

## 適用時機
- 使用者說「寫 change log」「幫我記錄今天的改動」「產生變更紀錄」時使用
- 目的是給**接手的同事**看：改了什麼、為什麼改、怎麼驗證、還有什麼坑沒填
- 與 `ops-daily-worklog` 的差異：worklog 是「今天做了哪些事」的流水帳，
  change log 是「程式碼/檔案實際變了什麼」的技術交接文件，**以異動內容為單位**而非時間軸

## 輸出路徑與命名

| 目錄 | 檔名格式 |
|---|---|
| `<repo>\public\Docs\ChangeLog\<EnglishName>\` | `CHANGES_{YYYYMMDD}_{作者}.md` |

> 所有專案共用同一目錄，不依專案分子目錄（同 ops-daily-worklog 慣例）。
> `{作者}` 用使用者本人英文名（例：Steven），不用專案名。
> **同一個人有兩台機器各自寫 ChangeLog 時**（Steven 20261005 17:0x）：第二台用 `<EnglishName>02` 當資料夾與檔名後綴，例 St02＝`<repo>\public\Docs\ChangeLog\Steven02\CHANGES_{YYYYMMDD}_Steven02.md`。入口網站 `tools/build_portal.py` 以「資料夾名＋日期」當一筆，同一資料夾同一天兩份會互相蓋掉。
> `D:\docs\ChangeLog\` 是 20260929 之前（St02 到 20261005）的舊位置，**不再寫新檔**；舊檔留著當史料。

## 輸出格式
純 **Markdown**，**不放 Logo**，不輸出 HTML（除非使用者另外要求）。

## 標頭標記慣例（強制，且要在報告第 0 節寫出來）

每處手動修改的程式碼都要在附近加上作者+日期標記，格式依語言而定：

| 語言 | 標頭格式 |
|---|---|
| C/C++、JavaScript | `//{作者} {YYYYMMDD}` |
| Python | `# {作者} {YYYYMMDD}` |
| HTML | `<!-- {作者} {YYYYMMDD} -->` |

- 若該專案本身已有既有的 AI 標記慣例（例如 HT9045 的 `//AI(AgentName) YYYYMMDD: 描述`），
  **兩種標記並存、不互相取代**——既有慣例維持專案自己的規則，新的 `{作者} {YYYYMMDD}` 標頭
  是給人看的快速定位標記，兩者可以標在同一行或緊鄰兩行。
- 標頭內容**只寫作者與日期，不要寫檔名**。曾發生過標頭裡多寫了完整檔名，
  結果被某個做「內容字串比對」的稽核工具（例如 kb_audit 之類的頁面接線稽核腳本）
  誤判成「這個檔案已經接了某功能」，統計整個灌水。**通則：加標頭前先想一下
  有沒有工具在對這個檔案的內容做字串/關鍵字掃描，標頭本身也是內容的一部分。**
- 報告第 0 節固定提供一行全樹搜尋指令，讓別人能自己列出當天全部改動點：
  ```
  grep -rn "{作者} {YYYYMMDD}" {專案根目錄} --include=*.cpp --include=*.h --include=*.js --include=*.py --include=*.html
  ```

## 固定章節結構

以下章節依內容有無決定要不要出現；沒有東西可寫的章節直接省略，不要留空節。

| # | 段落 | 內容 |
|---|---|---|
| 0 | 怎麼在程式碼裡找到這些修改 | 標頭標記表 + 全樹 grep 指令；若專案另有既有標記慣例，列出對照表 |
| 1 | 這天做了什麼（一句話版） | 一到兩句話講清楚目的，不用條列 |
| 2+ | 依模組/專案分節（如「C++ 後端」「前端」「刪除的檔案」）| 每個新增/修改點用表格列「行號/檔案 → 內容」，重要邏輯附程式碼片段（before/after） |
| — | 設計約束 | 用「改這段程式前務必先讀」小標，條列不可違反的規則與原因 |
| — | 已知的坑 / 陷阱 | 用 ⚠ 開頭，講清楚「怎麼踩到的」與「為什麼不報錯但是錯的」 |
| N | 怎麼自己驗證 | 具體指令 + 實測結果表格（不是「應該可以動」而是「已經測過，結果是這樣」）|
| N+1 | 已知落差（接手重點） | 編號清單，每項講清楚「缺什麼」「目前狀態」「風險等級」 |
| N+2 | 沒有標頭的檔案 | 格式不支援註解的檔案（如 .json）改了但沒法標記，列出來 + 為什麼改 |
| N+3 | 加標頭時踩到的坑 | 若有，記錄產生標頭/文件時自己踩到的意外（如上述 kb_audit 誤判案例）|
| N+4 | 安全邊界 | 重申本次改動**沒有**變更的既有安全規則（唯讀目錄、寫入邊界等），避免讀者誤以為邊界鬆動 |
| N+5 | 備份位置 | 表格：備份檔名 → 內容 → 大小；若有做過完整性驗證（如 `7z t`）要註明 |

## 寫作原則

1. **具體勝過摘要**：優先列出「檔案:行號」與實際程式碼片段，而不是「修改了 XX 邏輯」這種空泛描述。
2. **講清楚「為什麼」不只是「做了什麼」**：每個設計決策都要附一句原因，尤其是看起來「怪怪的」寫法。
3. **驗證要有實測結果，不能只寫步驟**：「執行 XXX，結果應該是 YYY」是不夠的，
   要寫「執行過，實測結果是 YYY」，並附數字/輸出對照表。
4. **誠實列出未完成與风险**：已知落差、TODO、尚未裁決的事項都要留在報告裡，
   不要為了讓報告好看而省略——change log 的價值就在於誠實的交接。
5. **安全邊界只重申、不擴權**：change log 不是變更安全規則的地方；
   若本次改動真的動到寫入邊界/唯讀範圍，那是需要使用者明確同意的另一件事，
   要在報告裡明講「本次是否有變更邊界」，預設答案是「沒有」。

## 產生流程

1. 蒐集當天所有修改：優先用 `grep -rn "{作者} {YYYYMMDD}"` 或 git diff / mtime 掃描
   （可借用 `code-diff-summary` 的 mtime 模式作為輸入來源）。
2. 依「固定章節結構」分節整理，模組分類可比照 `code-diff-summary.md` 的模組表。
3. 對每個新增行為，確認是否已在其他文件（Skill / AGENTS.md / 既有規格文件）留下對應更新，
   若有，在對應章節註明「已同步」。
4. 產生 metadata 表頭（見下）+ 內容，存至 `<repo>\public\Docs\ChangeLog\<EnglishName>\CHANGES_{YYYYMMDD}_<EnglishName>.md`。
5. 若使用者要求，另外附上一句話摘要供週報引用。

## metadata 表頭（檔案開頭，可選但建議）

```markdown
# {專案} 變更紀錄 — {YYYY-MM-DD}（{作者}）

本檔記錄 {YYYY-MM-DD} 當日對 {專案} 專案所做的全部修改，供同事查閱與接手。
```
