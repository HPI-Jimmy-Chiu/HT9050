## 1. HT9050 機台實際跑的出貨 exe **改用 oracle 建置**（選 A）

- 來源：使用者 20260926 經「機台端與筆電端進度同步」session 轉達（裁決 A）。題目見 `NIGHT_REPORT.md` 下午進度節的 🔔 項。
- 背景：機台一直跑 `build_integ_ship_x86`（WinLibs g++ 16.2、32-bit、`-std=c++14`），是處境沿用下來的
  （20260825 導入時機台沒有 `C:\MinGW` → 只能走非 oracle 線；x64 的 wb_publish 開機前就 heap 損毀 0xC0000374），沒有人裁決過。
  C++14 是被逼的：g++ 16 的 libstdc++ 在 C++17 下有 `std::byte`，跟樹裡的 `using namespace std;`＋w32api 的 `typedef unsigned char byte` 撞名。
- 裁決：**機台出貨 exe 改用 oracle ＝ `C:\MinGW` MinGW.org GCC 6.3.0、32-bit、C++17**（與筆電、CLAUDE.md「主 oracle 是 MinGW g++，唯一重現 BCB6 x87 算術」一致）。
- 機台端的步驟（機台端 session 已交代）：全新 build dir 評估 oracle 線能不能連結 `ADVMOT.lib`（連不上就評估 dlltool／gendef 重生 import lib）
  → ctest 失敗清單與筆電比 → EastSun 在場時上機只讀驗證 → 驗證過才把 F5 切過去；WinLibs 線保留作對照。擋路就停下回報，不繞道。
- 對 main 的影響：兩台 ctest 的基準會一致；機台樹自己加的 `HT9045_CXX_STANDARD`（c++14 降級）**不帶進 main 的 oracle 線**。
- 相關：`GA1_LastSet` 在 16.2 失敗的原因（C++ 的 `-fexcess-precision=standard`，GCC 13 起才實作）已在 main `dcceb23a` 改測試繞開；
  改用 oracle 後量產碼裡同類的浮點比較也會回到與 BCB6 一致的行為。
