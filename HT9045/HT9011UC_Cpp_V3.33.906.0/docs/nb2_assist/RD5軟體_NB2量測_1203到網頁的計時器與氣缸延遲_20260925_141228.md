## 0. 結論（給使用者）

1. **「網頁一按、底層立刻執行」基本上對，但不是無條件。**
   * 對 main 上 1203 頁（`web/pci1203.html`）的輸出按鈕是對的：WebSocket 立刻送出，伺服器收到後排入佇列。
   * 主迴圈只有一條執行緒，而且約 70% 的時間在讀卡（一次約 140 ms）。命令要等它讀完才會執行。
   * ⇒ 按下到線圈通電：**典型約 0.06 秒，最壞約 0.16 秒**。
   * 例外一：每 30 秒有一次讀 400 筆驅動器參數的窗口，推估卡住 0.4～4 秒，沒量過。
   * 例外二：命令被拒絕（沒有操作權、正在等警報回答、WebSocket 重連中）。這時不是「慢」，是「沒做」。
2. **正常情況下，我們這邊的軟體做不出「每次都慢 2 秒」。**
   * 按鈕 → 線圈 ≤ 0.16 秒。
   * 感測器 → 網頁燈號：典型 0.43 秒，最壞 0.92 秒。
   * 兩段加起來不含氣缸行程，最壞約 1.07 秒；頁面跳拍時約 1.57 秒。
3. **有一條路一定會超過 2 秒**：golden 引擎。
   * 引擎每 500 ms 才跑一次（B13 裁決；golden 約 1 ms）。手臂類是隔拍跑，實際 1000 ms 一次。
   * 氣缸一步（開閥 → 等感測器 → 延時）至少要跑 2～3 拍。
   * ⇒ **每一步 1.5～5.6 秒**。
   * main 上這條路碰不到 1203（`IOBackend.cpp:169-174` 是空的替身）。但**如果 P17 把按鈕接進了 golden 的 TMyCylinder／TLaneIO**，現場的 2 秒就是它。
4. **怎麼分出是不是我們這邊**：按按鈕時看 **1203 輸出模組那一路的 LED**（或電磁閥上的 LED）。
   * LED **立刻亮**、氣缸 2 秒後才動 ⇒ **氣路**的問題（氣壓、節流閥、電磁閥），不是軟體。
   * LED **2 秒後才亮** ⇒ **我們這邊**（P17 的路或主迴圈卡住），接著照 §5 量。
   * LED 立刻亮、網頁燈號慢 ⇒ 那是顯示慢，不是動作慢。改法看 §6 的 ②③。

## 1. 路徑圖（main）

```
【寫入】按下按鈕 ──► 線圈通電（只有 web/pci1203.html 會送；HW.IoSetView 在 main 不送）
  瀏覽器 click ─WS 立即─► 伺服器 socket 執行緒 ─排入佇列─► 主迴圈醒來取件 ─► Acm_DaqDoSetBitEx ─► EtherCAT ─► 電磁閥＋氣缸（非軟體）
        ~1 ms                    1–5 ms                  0–140 ms（在讀卡就等）      ~1 ms           1–10 ms（推估）
                                                        ＋偶發：30 s 窗口 0.4–4 s（推估）

【讀取】感測器 ──► 網頁燈號（HW.IoSetView）
  感測器 ─EtherCAT─► 1203 DI ─每 200 ms 讀一次卡（一次約 140 ms）─► 快取 ─網頁每 500 ms 用 HTTP 問一次─► 解析＋重畫
          1–10 ms            等 0–200 ms ＋ 讀卡內位置 0–90 ms                等 0–500 ms，HTTP ~10 ms      ~20 ms

【golden 引擎】（main 碰不到 1203；機台 P17 未知）
  引擎每 500 ms 一拍 ─► 手臂類隔拍 = 1000 ms ─► TMyCylinder::Push/Pop 要 2–3 拍 ─► 下一個動作再等 1 拍  ⇒ 每步 1.5–5.6 s
```

**「中間有幾個計時器」**：
* **讀取這條**：週期性計時器 **2 個**（伺服器每 200 ms 讀卡、網頁每 500 ms 問）＋會卡住的讀卡 1 段（約 140 ms）＋小段 3 個（EtherCAT、HTTP、重畫）。另外同一條執行緒上還有 500 ms 的 golden 引擎節拍，和 5 秒、30 秒兩個讀參數窗口。
* **寫入這條**：週期性計時器 **0 個**，是事件驅動。唯一的等待是「主迴圈正在忙」：讀卡最多 140 ms、跑引擎（沒量過）、30 秒窗口（沒量過）。

## 4. 「超過 2 秒」的可能原因（依可能性排序）

1. **現場跑的是 P17，不是 main**（最高，也最擋結論）。P17 讓 `HW.IoSetView` 的按鈕會送 `io.btnPanelClick`，但那條路沒人讀過。
2. **P17 若把按鈕接進 golden 的 TMyCylinder／TLaneIO**（高；每次都慢，不是偶發）：每步 1.5～5.6 秒，見 §3 ④。
3. **30 秒窗口**（中；偶發）：如果 2 秒是「有時候」，或者剛做過 gear／home 類命令，就是它。
4. **氣路**（中）：軟體典型 0.5 秒、最壞約 1.1 秒。氣缸行程若超過約 0.5～1 秒（氣壓低、節流閥鎖太緊、管路長），合起來就會超過 2 秒。
5. **主控台 QuickEdit**（中；偶發、沒有上限）。
6. **其實是被拒絕，不是慢**（低～中）：沒有操作權、正在等警報回答、WebSocket 重連中。操作員按了第二次才動，體感就是好幾秒。
7. 引擎裡的 `MySleep`、讀卡和引擎在同一圈疊在一起、連線數滿（16 條），都是低可能。

## 5. 現場量法（不改程式就能做）

0. 先問機台端 session 三件事：跑的是哪個 exe／分支；**按的是哪一頁、哪一顆按鈕**；慢的是「按 → 動」還是「動 → 燈」。拿到 P1～P17 的 diff。
1. **用手機慢動作（120～240 fps）同時拍螢幕、1203 輸出模組的 LED、氣缸**。
   * 按下 → 輸出 LED 亮：軟體寫入這段。
   * 輸出 LED 亮 → 氣缸到位：氣路這段。
   * 到位 → 輸入 LED → 網頁燈號：讀取這段。
   * **這一步就能回答「是不是我們這邊」。**
2. 在機台上用 PowerShell 每 100 ms 抓一次 `/api/struct/io/runtime`，抓 2 分鐘，記下 `pollCount`、`pollMs`、`pollErrors`。
   * `pollCount` 應該每秒增加約 5。
   * 每 30 秒出現一次停頓，或 `pollMs` 跳到 >400，就是 30 秒窗口，順便量到它真正的成本。
3. 瀏覽器 DevTools：
   * WS 分頁：從 `pci1203.do.setBit` 送出到收到 ack 的時間，就是「按 → 線圈」的軟體延遲。
   * Network 分頁：`runtime?_=` 請求的間隔（應為 500 ms，出現 1000 ms 表示跳拍）和大小。
4. 每 3 秒按一次 DO，連續 2～3 分鐘，記 ack 時間。
   * 穩定在 50～150 ms ⇒ 軟體寫入這段正常，2 秒在別處。
   * 每 30 秒出現一次尖峰 ⇒ 30 秒窗口。
5. 關掉 wb_serve 主控台的「快速編輯模式」再測一次。
6. 用 Common Motion Utility 讀 EtherCAT 週期與 DI 濾波時間。我們的程式從來沒讀過這兩個值。

## 8. 誠實聲明

* 時間數字只有「讀卡 140 ms」和「點擊到燈號 347 ms」是實測。兩個都是同事在 wb_publish 上量的，不是 A 樹的 wb_serve。其餘都是從程式碼推算。
* 引擎一拍的成本、每筆 SDO 的成本、組 JSON 與瀏覽器重畫的時間，都**沒量過**。
* 讀卡的呼叫數有兩種說法：註解寫「172 DI＋94 DO 埠」，另一處註解寫「744 DI 通道＝93 埠」。所以每個呼叫約 0.33 ms 這個推算有不確定性。
* **P17 沒看過**：那才是現場在跑的碼。
