# 給 Steven 的「網頁缺件」通知規則（提案，NB2 起草；使用者 20260925 10:1x 要求）

> 使用者原話：「web畫面需要有，可先從steven提供的參考，他通常是透過BCB6開發的樣式照翻過來，如果缺少web都要告知，
> 為了避免過度濫發信件，針對給Steven必須立即補齊的資料，需要寄信通知改善，但是我考慮到不要過多信件造成轟炸」
>
> 目標是兩件事：**缺件一件都不漏**，**信件數量壓到最少**。

## 1. 一本帳：`docs/STEVEN_REQUESTS.md`（新電腦維護；NB2 不能寫那裡，只能在自己的 README 提報候選）

每一個缺件記一列，**先記帳，再決定要不要寄信**：

| 欄位 | 內容 | 例 |
|---|---|---|
| 編號 | `SR-001` 起流水號，永不重用 | SR-007 |
| 發現日 | YYYYMMDD | 20260925 |
| 缺什麼 | 哪一頁、哪個欄位／按鈕／JSON 鍵 | RS232 面板的按鍵狀態頁（golden `uPadInterface` 表單） |
| 為什麼要 | 對到哪個 C++ 功能、golden 表單名與行號 | W3-4b 面板鍵翻完後，網頁上沒地方看到按鍵狀態 |
| 急迫度 | 🔴 擋住「機台跑起來」／🟡 功能要完整才需要／🟢 好用而已 | 🔴 |
| 先查過 | 已確認 Steven 現有的參考頁、JSON、共用區裡**沒有** | 查過 `web/page/*.html`、`JSON/*.json`、pagewire 普查 |
| 暫代做法 | 等 Steven 補之前，新電腦怎麼撐 | 先用 Steven 現有的 `HW.*` 頁的樣式做最小版，標「暫代」 |
| 狀態 | 新增／已寄信 YYYYMMDD／Steven 已交／關閉 | 已寄信 20260925 |

**記帳之前先查**：使用者說「可先從 Steven 提供的參考」。所以確認他**真的沒有**才算缺件。
他通常照 BCB6 表單樣式翻，同一個畫面可能已經有了、只是換了名字。

## 2. 寄信規則

1. **只有 🔴 會觸發寄信。**🟡、🟢 不單獨寄，搭下一封 🔴 的信，或放進每週彙整。
2. **一天最多一封。**當天新增的 🔴 累積起來，在固定時間（建議下班前 17:00）合成一封。當天沒有新的 🔴 就不寄。
3. **每週一封彙整**（建議週三，和週報同一天）：列出所有還沒補的 🟡、🟢。**跟上週比沒有變化就不寄。**
4. **同一件不重寄。**只有狀態變了，或 🔴 超過 3 個工作天還沒補，才在下一封信的「仍未補」段落再出現一次，不另外寫一封。
5. **每封信寄出前先給 Jimmy 看全文**（收件人、副本、內容）。Jimmy 同意才寄，信的副本加 Jimmy。
   日後 Jimmy 可以改成「每日那封直接寄」的常設授權。
6. **信的格式**：標題固定 `[HT9045 V906] 網頁缺件 YYYYMMDD（🔴 N 件）`；內文只列本次新增與仍未補的編號、一句話說缺什麼和為什麼；附帳本檔的路徑與 commit。**不附檔案**。

## 3. 舉例（一週可能長這樣）

* 週一新電腦翻 uPadInterface，發現 3 件缺：面板鍵狀態頁是 🔴，除錯頁、手動送出是 🟡。
  ⇒ 記帳 SR-007～009，週一 17:00 寄**一封**，只講 SR-007，並附一句「另有 2 件非急，週三彙整」。
* 週二又發現 1 件 🔴 ⇒ 週二 17:00 寄一封，只講這一件。
* 週三彙整信列 SR-008、SR-009（🟡）；SR-007 如果還沒補，也列在「仍未補」。
* 週四、週五沒有新的 🔴 ⇒ **不寄**。

⇒ 一週 3 封，而不是每發現一件寄一封（7 件＝7 封）。
