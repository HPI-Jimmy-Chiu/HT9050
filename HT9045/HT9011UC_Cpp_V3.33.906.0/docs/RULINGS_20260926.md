## 1. HT9050 機台實際跑的出貨 exe **改用 oracle 建置**（選 A）

- 來源：使用者 20260926 經「機台端與筆電端進度同步」session 轉達（裁決 A）。題目見 `NIGHT_REPORT.md` 下午進度節的 🔔 項。
- 背景：機台一直跑 `build_integ_ship_x86`（WinLibs g++ 16.2、32-bit、`-std=c++14`），是處境沿用下來的
  （20260825 導入時機台沒有 `C:\MinGW` → 只能走非 oracle 線；x64 的 wb_publish 開機前就 heap 損毀 0xC0000374），沒有人裁決過。
  C++14 是被逼的：g++ 16 的 libstdc++ 在 C++17 下有 `std::byte`，跟樹裡的 `using namespace std;`＋w32api 的 `typedef unsigned char byte` 撞名。
- 裁決：**機台出貨 exe 改用 oracle ＝ `C:\MinGW` MinGW.org GCC 6.3.0、32-bit、C++17**（與筆電、CLAUDE.md「主 oracle 是 MinGW g++，唯一重現 BCB6 x87 算術」一致）。
- 機台端的步驟（機台端 session 已交代）：全新 build dir 評估 oracle 線能不能連結 `ADVMOT.lib`（連不上就評估 dlltool／gendef 重生 import lib）
  → ctest 失敗清單與筆電比 → EastSun 在場時上機只讀驗證 → 驗證過才把 F5 切過去；WinLibs 線保留作對照。擋路就停下回報，不繞道。
- 對 main 的影響：兩台 ctest 的基準會一致；機台樹自己加的 `HT9045_CXX_STANDARD`（c++14 降級）**不帶進 main 的 oracle 線**。
- 相關：`GA1_LastSet` 在 16.2 失敗的原因（C++ 的 `-fexcess-precision=standard`，GCC 13 起才實作）已在 main `dcceb23a` 改測試繞開；
  改用 oracle 後量產碼裡同類的浮點比較也會回到與 BCB6 一致的行為。

## 6. HT9050 的 INDEX_MOTION_CARD：**ini 不改，程式裡繞**（EastSun 20260926，經機台端 session 轉達，0926 07:1x）

- 起因：筆電 0926 07:0x 提醒 —— 機台正本 `Gerneral.ini` 是 `INDEX_MOTION_CARD=0`；golden 只比 `==0`，等於 0 時 `InitialMotorParameter` 把 Index 四軸（M13～M16）
  直接建成 `TMyGALILMotor`、完全不看 Mot_Table（`docs/W3_PROGRESS.md:281-282`，W3-10 量過）。機台端只讀查證屬實：`MOT[MTestZ1].CardType` 前一行已從表設成 "PCI1203"，
  物件卻是 Galil；Motor Test 頁的「M14 走 1203」是 `WebMotorAccessLive.cpp` 的 R2 掛鉤自己把 M14 當 1203 處理，**引擎裡的 M14 一直是 Galil**。
- 裁決：**ini 檔不動**。讀完 INDEX_MOTION_CARD 與馬達表之後，**若表上 MTestZ1 是 PCI1203，就把記憶體裡的 INDEX_MOTION_CARD 當成 1**；
  效果等於 ini=1：四軸照表建（M14→TMyEtherCatMotor，M13／M15／M16 照表停用），全樹約 30 處 `INDEX_MOTION_CARD==0` 自動走「照表」那一臂。
  **只在「表上 MTestZ1 是 PCI1203」時生效，其他機種照 golden 用 ini 的值。** 全樹沒有任何地方把 INDEX_MOTION_CARD 寫回 ini（機台 git grep 過）。
- 誰做：**機台**（與第 2 條「甲」一起做），改動點在 `database.cpp`／`cinitial.cpp` 讀馬達表、讀 INDEX_MOTION_CARD 的那一帶 ⇒ 筆電先不要動（INBOX 第 34 列）。
- 對筆電 G03（`eed5033b`）的影響：生效後 HT9050 記憶體裡是 1，G03 所在的 Galil 那一臂不會進去；G03 照 golden 開，不用改。
